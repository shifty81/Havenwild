## Baseline and cause

The user's **R7** Windows PCC gate finished GREEN and the candidate built, ran, and visibly displayed source pixels. **R8 has not been independently Windows-certified.** In the first candidate launch log (Windows 10; GTX 1080 Ti; NVIDIA 582.66; *actual* Vulkan adapter), the presentation-layout VUID `VUID-VkPresentInfoKHR-pImageIndices-01430` and acquire-semaphore VUID `VUID-vkAcquireNextImageKHR-semaphore-01286` each generated ten `VALIDATION [...]` headings at startup. The user then closed the window and Cargo reported exit 0. R8 repaired the old PCC numeric exit-code conflation but did not repair Vulkan. Independent upstream Bevy reports include https://github.com/bevyengine/bevy/issues/22733 and https://github.com/bevyengine/bevy/issues/22744; similarity alone does **not** prove identical root cause, a version-level fix, or driver culpability.

## Windows verification procedure: one GREEN gate, four controlled launches

1. Back up/preserve your R7 GREEN evidence; close Bevy and ForgePY. Place **only the R9 cumulative ZIP** in the test project root. Apply with `HavenwildTools.cmd` and run `FULL QUALITY GATE`. Don't commit or push until **R9** is actually Windows GREEN. A failed gate must be diagnosed from its complete action/debug log, not from a stale GUI banner.
2. Under the same PCC `Run & Play` menu, launch **normal Bevy candidate**, the baseline full setup and default/automatic backend. Record the *actual* `AdapterInfo backend:` (not merely `WGPU_BACKEND`) and whether the two specific validation VUIDs occur; inspect a screenshot, select a river tile, Fit/zoom/pan/grid, and close. Confirm candidate operation shows a numeric exit code; zero alone is not GPU clean.
3. Launch **Bevy diagnostic: DX12 full candidate**. Confirm `AdapterInfo backend: Dx12` (or record the actual value), compare VUIDs and screenshot. Do not infer backend from requested mode.
4. Launch **Bevy diagnostic: primary window only / auto backend**. Verify that the window and GUI render and the river texture is absent *by design*. Compare validation VUIDs.
5. Launch **Bevy diagnostic: primary window only / DX12**. Again verify actual adapter backend, startup validation messages and normal close. This isolates primary swapchain from the two offscreen cameras without suppressing Vulkan validation.
6. Capture separate PCC action logs and run `python experiments/haven_bevy_candidate/tools/gpu_validation_audit.py --log "<path to Bevy action log>"` against each existing complete log (maximum 32 MiB). A missing VUID is evidence **only for the provided log**; screenshots, driver/renderer state and consistent repeated runs are still needed.
7. If both full and primary-only Vulkan modes reproduce, investigate upstream wgpu/Bevy/Vulkan validation/driver before editing ElizaWy mapping. If only full reproduces, inspect Bevy offscreen target/camera scheduling. DX12 comparisons are diagnostics, not a permanent backend switch. Do not disable validation or automatically promote a renderer merely because it opens.
